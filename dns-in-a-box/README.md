# DNS in a Box

DNS in a Box is a starter package for BlueCat DNS GitOps. The workflows in this folder are templates. To deploy, copy the contents of this folder, including hidden files, to the root of a dedicated private repository. Configure Jira, GitHub, and BlueCat there using the setup below.

A Jira Service Management Cloud request becomes a GitHub pull request. The DNS team reviews the exact before and after states. A protected merge sends the request to a dedicated internal runner. That runner checks Jira, compares the live BlueCat Address Manager (BAM) object and authoritative DNS with the approved state, performs the change, requests BlueCat Quick Deploy, and polls every configured authoritative server. Jira gets an internal comment with the PR or workflow run link.

## Scope

This is a Git journal of approved, one-time changes. Each pull request adds one immutable request file. Existing DNS records stay under BAM ownership. The pipeline supports create, in-place update, and delete for A, AAAA, CNAME, TXT, MX, SRV, PTR, and CAA, subject to the zone allowlist and the lab acceptance gate below.

A and AAAA use native HostRecord objects with existing IPAM address references, one address family per object, and reverse creation disabled. CNAME, MX, and SRV use existing same-view BAM Host or External Host objects. PTR is a separate GenericRecord request in an eligible reverse zone. The automated lane allows one BAM object per owner and type, with up to 16 addresses on a native host. Apex TXT, MX, or CAA and wildcard owners require explicit zone opt-in. Updates keep the owner, record type, and object ID. Linked hosts with dependent records, mixed-family hosts, multiple native HostRecord objects at one owner, duplicate objects of the same type, inherited TTL, multi-string TXT, delegation and glue, SOA, DNSSEC, HTTPS/SVCB, zone management, bulk changes, and renames go to DNS Engineering. Coordinated multi-record changes, including an owner switching between A and CNAME, also use that workflow.

## Set up the pilot

1. **Confirm the BlueCat product and version.** The provider is built for BlueCat Integrity Address Manager REST v2 and uses the 25.1/26.1 documentation as its baseline. Open `https://<primary-bam>/api/docs` and check the live schema. Verify the exact HostRecord reverse flag, address reference and response fields, zone/view and parent links, inherited versus explicit TTL, linked-record types and fields, dependent-record responses, PTR/CAA support, PUT behavior, and the QuickDeployment body on your release. The BlueCat appliance schema and lab results determine which types you enable. Start with A and CNAME in one lab view.
2. **Set zone policy.** Edit [config/zones.json](config/zones.json). Replace sample IDs, names, and authoritative IPs. Create separate zone keys and IDs for split-horizon views, even when the DNS name is identical. Use the source network that actually selects the intended view. Provide every authoritative server that must confirm the change and permit TCP/53 from the runner. Use the approved record type list, critical-name denylist, and window flag. Keep production zones disabled through lab acceptance.
3. **Protect the private GitHub repository.** Import these files at the root. Replace the CODEOWNERS teams. On `main`, require pull requests, DNS CODEOWNERS approval, dismissal of stale approval after new commits, an up-to-date branch, and the **Validate DNS request** check. Disallow bypass, force pushes, and branch deletion. Use individual squash merges and preserve the generated request title. Use a separate rule for `dns/*` so the automation identity alone can push request branches. Keep the automation identity out of approver teams and allow the account to open pull requests. Source, workflow, and zone-policy changes need the maintainers' review in separate PRs. Avoid commit messages that skip Actions.
4. **Create runner group and environments.** Create the `bluecat-dns` group, restrict it to this repository and `OWNER/REPO/.github/workflows/deploy.yml@main`, and give exactly one dedicated Linux runner the `bluecat-dns-singleton` label. Create a private, writable, persistent state directory outside the checkout, owned by the runner account with mode 0700. Install Git, Python 3.10+, and BIND `dig` (Ubuntu `dnsutils`). The runner needs HTTPS access to Jira, GitHub, and primary BAM and TCP DNS access to the configured authorities. Restrict both GitHub environments, `dns-intake` and `dns-apply`, to `main`. Put required environment reviewers on `dns-apply` if your change policy requires a second gate. The workflow uses a singleton runner to serialize provider writes without dropping queued jobs through an Actions concurrency group. Keep PR checks on GitHub-hosted runners.
5. **Set credentials.** Configure the variables and secrets below. Use a dedicated least-privilege BAM account scoped to enabled views/zones, with read access to address and link metadata and the right to Quick Deploy. Reserve that account for this pipeline. BlueCat Quick Deploy can publish other pending changes made by the same account on the same primary server. Establish a break-glass handoff and prohibit concurrent console, DDNS, or other automation writes at owners managed through this lane. The read/compare and write are separate BAM API calls.
6. **Configure Jira.** Follow [Jira form and Automation](jira/FORM_AND_AUTOMATION.md), fill in [config/jira.json](config/jira.json), and set the automation action to send [dispatch.json](jira/dispatch.json). Start by dispatching an approved pilot ticket manually from GitHub Actions to validate the Jira field mapping before enabling Jira's Automation rule.
7. **Run the lab acceptance matrix.** Record the BAM build, request PR, authoritative results, and observed deployment status. Enable each production type only after its matrix passes in a representative view. Production, internal, and public views can have different outcomes even on the same appliance.

| Where | Setting | Value |
| --- | --- | --- |
| Both GitHub environments | Variable `JIRA_URL` | Your Jira HTTPS origin, such as `https://company.atlassian.net` |
| Both GitHub environments | Secrets `JIRA_USER`, `JIRA_TOKEN` | Jira service account email and approved API token for direct Jira Cloud REST. Grant access to the dedicated JSM project and internal comments |
| `dns-intake` | Secret `DNS_PR_BOT_TOKEN` | Fine-grained machine-user token limited to this repo with Contents and Pull requests read/write. Its identity must trigger PR checks |
| `dns-apply` | Variable `DNS_STATE_DIR` | Absolute path to the private persistent state directory, such as `/var/lib/bluecat-dns-gitops` |
| `dns-apply` | Variable `BAM_URL` | Primary BAM HTTPS origin, with system trust or a configured private CA |
| `dns-apply` | Variable `BAM_CA_FILE` | Optional absolute path to a trusted PEM CA bundle installed on the runner |
| `dns-apply` | Secrets `BAM_USER`, `BAM_PASSWORD` | Dedicated BAM API account |
| Jira rule | Hidden Authorization header | Separate GitHub credential limited to this repo with Actions write for workflow dispatch |

## Lab acceptance and operational recovery

- For each enabled type, create, update, delete, and retry on a disposable owner. Verify the correct split-horizon view, exact TTL/RDATA, correct object identity, and success comment. For A/AAAA verify IPAM objects are preserved and no automatic PTR is generated. For PTR verify standalone reverse record handling on your BAM version. For apex, wildcard, and linked external names test those features separately if enabled.
- Reject the wrong view, existing conflicting record, unauthorized Jira state, stale Jira fields, changed live value/TTL, protected owner, CNAME coexistence, a linked host with dependencies, and any closed window. Verify a non-authoritative response fails the job. Confirm you can use deployment reports to inspect a staged but unverified change.
- GitHub PR validation previews the submitted change without contacting BAM. The apply job checks live state again immediately before writing. Approve and merge during the requested UTC window. A window is an execution gate, with no automatic scheduler. Keep the Jira issue in the configured approved status until verification.
- If an apply fails during or after a write, its pending marker stops other tickets from using Quick Deploy. Inspect the workflow, BAM deployment reports, and each authoritative server. After resolving the cause and confirming the expected state is still valid, rerun the original deployment job within its window. A staged change can be published without repeating the mutation. A newer request for that owner or a later policy/code change makes the old job ineligible. For an expired window, coordinate recovery with DNS Engineering using a new Jira request or approved manual deployment and document it on the original ticket. After confirming that this service account has no other pending changes and that authoritative DNS is correct, the operator can clear the pending-change marker to reopen the queue. Preserve the state directory during runner replacement.
- To roll back, open a new Jira ticket with the inverse change, using the *actual current* object ID, value and TTL. Re-creating a deleted record gives it a new object ID. The request journal is append-only and a Git revert does not restore DNS. Recursive clients can retain old or negative answers until their cache TTL expires.
- A failed Jira success comment can make the job appear failed even when DNS is verified. Check the job output and authoritative data before taking recovery action. Intake and deployment post internal comments. Any Jira Done/Failed transitions should be configured in your workflow policy.

## Local checks

Run `python3 -m unittest discover -s tests -v` from the repository root. The package was exercised with mocks and sample requests. The target BAM, GitHub, and Jira instances were unavailable for live integration testing.
